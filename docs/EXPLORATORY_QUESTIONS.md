## ✦  탐구 질문

### ✧  자동 복구

- 🔭 탐구 질문
    
    **1. 장애 시나리오 분석** (최소 4가지 시나리오 식별)
    
    여러분의 시스템에서 발생할 수 있는 장애를 구체적으로 상상해보세요. 각 장애마다 원인과 복구 방법이 다릅니다.
    
    - 애플리케이션이 OutOfMemoryError로 크래시되는 경우는 어떻게 감지하고 복구할 수 있나요?
        
        → 감지 방법: 
        
        1. CloudWatch Logs: `java.lang.OutOfMemoryError` 패턴 감지
        2. CloudWatch Alarm: TaskMemoryUtilization > 80% 지속
        
        → 복구 방법:
        
        1. ECS의 자동 재시작 기능: Task가 종료되면 자동으로 새 Task가 생성됨
        2. AutoScaling: Memory 기반 autoscaling을 켜면 메모리 부족 Task가 생기기 전에 scale-out
    - ECS Task가 실행 중인 물리 호스트에 하드웨어 문제가 생긴다면?
        
        → 감지 방법:
        
        1. AWS 자동 감지
            1. AWS가 Fargate 인프라의 상태를 자동으로 모니터링
            2. 하드웨어 문제 발생 시 AWS가 자동으로 감지
        2. CloudWatch 메트릭: 
            1. CloudWatch Container Insights로 Task 레벨 메트릭 모니터링
        
        → 복구 방법:
        
        1. AWS가 자동으로 다른 물리 호스트에서 Task 재시작
        2. 최소 2개 이상의 Task를 서로 다른 AZ의 서브넷에 분산 배치
    - 데이터베이스가 응답하지 않는다면 애플리케이션은 어떻게 되나요?
        
        → 어플리케이션 레벨에서 Connection timeout 또는 query timeout 발생
        
        → 사전 대응 : RDS Multi-AZ 배포로 Primary 장애 시 60-120초 내 Standby로 자동 failover
        
    - 한 가용영역(AZ) 전체에 장애가 발생하는 극단적인 상황에서는?
        
        → ECS Fargate Task를 여러 AZ의 서브넷에 분산
        
        → RDS Multi-AZ 자동 failover
        
        → ALB가 정상 AZ의 Target으로만 트래픽 라우팅
        
    
    **2. AWS 자동 복구 기능 조사**
    
    각 기능이 어떤 문제를 해결하는지, 어떻게 작동하는지 직접 조사해보세요.
    
    - ECS Health Check는 어떤 방식으로 Task의 건강 상태를 판단하나요?
        
        태스크 정의에 상태 확인이 정의된 경우, 컨테이너는 컨테이너 내 상태 확인 프로세스를 실행하고 종료코드를 평가하여 애플리케이션 상태를 확인
        
        `HEALTHY` : 컨테이너의 상태 확인을 성공적으로 통과
        
        `UNHEALTHY` : 컨테이너 상태 확인에 실패
        
        `UNKNOWN` : 컨테이너 상태 확인을 평가 중이거나, 정의되지 않았거나, ECS에서 컨테이너 상태를 알 수 없을 때
        
    - Health Check가 실패하면 정확히 무슨 일이 일어나나요?
        - Container Health Check (`Task Definition`)
            
            컨테이너 내부 애플리케이션 상태 확인 → 실패 시, 컨테이너를 재시작
            
        - Target Group Health Check (`ALB, Application Load Balancer Target Group`)
            
            외부 트래픽 라우팅 결정 → 실패 시, 트래픽 차단
            
        - Health Check Grace Period (`ECS Service`)
            
            Task 강제 종료 방지 → 지정 시간동안 Health Check 실패를 허용
            
    - Multi-AZ 배포는 왜 필요하고, Single-AZ와 비교했을 때 어떤 장점과 단점이 있나요?
        - Multi-AZ 배포의 필요성
            
            한 AZ에 정전, 화재, 네트워크 장애 등의 문제가 생기면 해당 AZ 내의 모든 서비스들이 중단될 수 있음
            
            이러한 상황을 대비하여 다른 AZ에 동일한 리소스를 준비하여 자동으로 Failover가 가능하도록 만들어 서비스 중단을 피함
            
            Single-AZ의 경우, AZ 장애 발생 시 서비스가 전체 다운이 되지만 Multi-AZ는 다른 AZ에서 무중단 운영이 가능
            
            하지만 여러 AZ에 서비스를 배치해야하므로 비용이 증가
            
    - RDS의 자동 Failover는 어떻게 작동하며, 얼마나 시간이 걸리나요?
        
        스탠바이 데이터베이스로 failover를 시도 (⌚️ 60 - 120 sec)
        
        기존 원본 데이터베이스가 가지고 있던 접속 정보(인스턴스 접속 엔드포인트)를 그대로 물려받음
        
    - Auto Scaling은 "자동 복구"인가요, 아니면 "자동 확장"인가요? 이 둘의 차이는 무엇인가요?
        
        Auto Scaling은 두 기능을 모두 포함
        
        - 자동 복구(Auto Healing)
            
            실행 중인 인스턴스나 Task가 중단될 시 동일 개수로 유지
            
        - 자동 확장(Auto Scaling)
            
            트래픽에 따라 Task 개수를 늘리고 줄임
            
    
    **3. 자동 복구 불가능한 경우**
    
    모든 장애가 자동으로 복구될 수 있는 것은 아닙니다. 다음 상황에서는 어떻게 대응해야 할까요?
    
    - 애플리케이션 코드에 버그가 있어서 Task가 시작하자마자 크래시하고, 이것이 무한 반복된다면?
      
        - 즉시 대응
          
            1. ECS 서비스의 desired count를 0으로 설정해서 불필요한 재시작을 멈춘다.
            2. CloudWatch Logs에서 크래시 원인을 파악한다
            3. Task 정의를 이전의 안정적인 버전으로 롤백하거나, 버그를 수정한 새로운 이미지를 빌드해서 배포한다.
        - 예방 방법
          
            - 배포 전에 충분한 테스트를 거치고, Blue-Green 배포에서 deployment circuit breaker를 활성화해서 실패 시 자동으로 롤백되도록 설정.
            - 헬스체크를 강화해서 애플리케이션이 정상적으로 시작되었는지 확인하고, startPeriod를 충분히 길게 설정해서 초기화 시간을 확보.
    - 데이터베이스 디스크가 가득 차서 더 이상 쓰기가 불가능하다면?
      
        - 즉시 대응
          
            1. 오래된 로그 테이블이나 임시 데이터를 삭제해서 공간을 확보하고, AWS 콘솔에서 RDS 스토리지를 긴급 확장한다.
        - 예방 방법
          
            1. 스토리지 확장은 다운타임이 발생할 수 있으므로, 사전에 RDS의 Storage Autoscaling을 활성화해서 디스크 사용량이 일정 수준을 넘으면 자동으로 확장되도록 설정한다.
            2. CloudWatch Alarm을 설정해서 디스크 여유 공간이 20GB 이하로 떨어지면 경고 알림을, 10GB 이하면 긴급 알림을 받는다.
            3. 장기적으로는 오래된 데이터를 정기적으로 S3로 아카이빙하는 배치 작업을 스케줄링해서, 데이터베이스에는 최근 데이터만 유지하도록 관리한다.
    - 드물지만 AWS 리전 전체에 장애가 발생한다면?
      
        - 즉시 대응
          
            1. 미리 준비해둔 DR환경으로 전환.
            2. Route53 헬스체크가 자동으로 트래픽을 DR로 라우팅 시켜 주지만, 작동하지 않을 경우 수동으로 전환.
            3. DR 리전의 Read Replica를 Master로 승격 시켜 쓰기 작업 처리.
            4. ECS 서비스를 스케일 아웃해 Task 확보.
        - 예방 방법
          
            1. DR 리전에 Standby 환경을 구축하는 Active-Passive 구조가 설정.
            2. Route53 헬스체크와 Failover 라우팅으로 자동 전환을 설정하고, RDS Cross-Region Read Replica로 데이터를 실시간 복제.
            3. 정기적인 페일오버 훈련으로 시스템을 검증하고, 명확한 을 작성해서 팀원들과 공유하며, 가능한 부분은 스크립트로 자동화.

### ✧  Auto Scaling

- 🔭 탐구 질문
    
    **1. Auto Scaling 트리거 선택**
    
    서버를 언제 늘려야 할까요? 다양한 옵션이 있고, 각각 장단점이 있습니다.
    
    - CPU 사용률 70% 초과 시: 가장 일반적이지만, CPU가 높다고 항상 성능이 나쁜 건 아닙니다.
    - 메모리 사용률 80% 초과 시: 메모리 부족은 OutOfMemory로 이어져 치명적이지만, 측정이 복잡합니다.
    - HTTP 요청 큐에 대기 중인 요청 수: 실제 처리 능력 부족을 직접적으로 나타냅니다.
    - 응답시간 95 백분위수 800ms 초과: SLA 위반 직전이므로 명확한 신호이지만, 이미 느려진 후입니다.
    
    각 방법의 장단점을 비교하고, SwiftLogix에 가장 적합한 방법은 무엇일까요?
    
    |  | 장점 | 단점 |
    | --- | --- | --- |
    | CPU 사용률 | 클라우드 플랫폼에서 기본 제공되는 메트릭이라 별도 설정 없이 즉시 사용 가능하고 계산 비용이 낮다. | CPU 사용률만으로는 실제 애플리케이션 성능을 정확히 반영하지 못하고, I/O 대기나 네트워크 병목 같은 다른 원인의 성능 저하를 감지할 수 없다. |
    | 메모리 사용률 | 메모리 부족은 OutOfMemoryError로 인한 즉각적인 장애를 유발하므로, 사전 스케일링으로 치명적인 장애를 예방할 수 있다. | 실제 사용 메모리와 캐시 메모리 구분, 런타임별 메모리 관리 방식 차이 등으로 측정과 임계값 설정이 복잡하고, 메모리 누수 같은 근본 원인을 해결하지 못한다. |
    | HTTP 요청 큐 대기 수 | 서버의 실제 처리 능력 부족 상황을 직접적으로 측정하여 가장 정확한 스케일링 신호를 제공한다. | 큐 메트릭 수집을 위한 추가 설정이 필요하고, 적절한 임계값 결정이 어려우며 순간적인 트래픽에 과하게 반응할 수 있다. |
    | 응답시간 95 백분위수 | 실제 사용자 경험과 SLA를 직접 반영하며, 모든 종류의 병목 현상을 종합적으로 감지할 수 있다. | 이미 성능이 저하된 후에 반응하는 사후 대응 방식이며, 외부 의존성 문제는 인스턴스 증설로 해결되지 않을 수 있다. |
    
    가장 적합한 방법
    
    **`응답시간 95 백분위수 800ms 초과`**
    
    계약서에 "p95 응답시간 1초 초과 시 위약금"이라고 명시되어 있으므로, 800ms를 기준으로 스케일링하면 1초 도달 전에 미리 대응이 가능하고,
    
    CTO가 "절대 느려서는 안 된다"고 강조했기 때문에 응답시간이 가장 직접적인 지표가 될 수 있기 때문이다.
    
    **2. Task 개수 범위 설정**
    
    최소 Task와 최대 Task 개수를 어떻게 정할까요?
    
    - 한 Task가 초당 몇 개의 요청을 처리할 수 있다고 가정해야 할까요?
      
        - Fargate 0.25 vCPU는 성능이 좀 떨어지기 때문에 `초당 100개`가 안전하다고 판단
    - 평소 트래픽(초당 20 req)을 처리하려면 최소 몇 개의 Task가 필요할까요?
      
        - 초당 100개를 처리할 수 있기 때문에 1개면 충분하지만 `고가용성을 위해 2개`가 안전
    - 고가용성을 위해 여유분을 얼마나 둘 건가요?
      
        - `2배의 여유분`(장애 상황 + 배포 상황)
    - 블랙프라이데이(초당 200 req)를 처리하려면 최대 몇 개까지 필요할까요?
      
        - 이론상 2개가 적당하지만 SAL 위약금과 순간적으로 더 높은 트래픽을 위해 `5개정도`가 필요
    - Task를 늘릴 때 한 번에 1개씩? 2개씩? (빠른 대응 vs 비용 절감)
      
        - SLA 위약금 25만원 생각하면 `2개씩`이 합리적
    
    **3. 블랙프라이데이 대응 전략**
    
    Auto Scaling은 기본적으로 **반응적**입니다. 문제가 생긴 후에 대응하는 거죠. 하지만 블랙프라이데이는 정확히 언제 트래픽이 급증할지 알고 있습니다.
    
    - 반응적 Auto Scaling의 문제점: Task 시작에 30초-1분 소요, 그 사이 기존 Task 과부하
      
    - **Scheduled Scaling**: 블랙프라이데이 당일 오전 8시에 미리 Task를 최대로 늘려놓기
      
    - **Warm Pool**: 미리 시작된 컨테이너를 대기 상태로 두었다가 즉시 활성화
      
    - 어떤 전략이 SwiftLogix에 적합할까요?
      
        - **반응적 Auto Scaling**은 추가 설정이 필요없고, 비용 최소한으로 들지만 이미 느려진 후 대응하기 때문에 SLA 위반 위험 높다. `적합하지 않음`
        - **Warm Pool** 방식은 즉각 대응이 가능하다는 장점이 있지만, ECS Fargate에선 지원하지 않고 대기중인 Task에서도 비용이 발생하며, 구현이 복잡하다. `적합하지 않음`
        - 선택지 중 가장 적합한 방식은 **Scheduled Scaling**으로 설정이 간단하고 트래픽 급증 전에 미리 준비가 가능하다. 하지만 시간 예측에 실패하면 소용이 없다는
        - 위험성이 있지만, 그간 데이터를 통해 예측이 거의 가능할 것이라고 판단된다. `가장 적합`
    
    **4. 현실적 우선순위 판단**
    
    72시간이라는 제한된 시간 안에 무엇을 해야 하고, 무엇을 나중으로 미뤄도 될까요?
    
    지금 (런칭 전 72시간)
    
    - Multi-AZ 배포로 고가용성 확보
    - 고정된 Task 개수로 시작 (예: 각 서비스당 2개)
    - 수동으로 Task 개수를 조정할 수 있는 구조
    - CloudWatch로 실제 트래픽 패턴 모니터링 시작
    
    나중 (런칭 후 1-2주)
    
    - 1주일간 실제 트래픽 데이터 수집
    - CPU, 메모리, 응답시간 패턴 분석
    - Auto Scaling 정책 설계 및 테스트
    - 블랙프라이데이 1주 전 최종 검증
- 학습 내용 정리
  
    - Auto Scaling
      
        - 오토 스케일링은 트래픽 변화에 따라 Task 수를 자동으로 늘리거나 줄이는 기능이다.
        - 만약 평소 2개의 Task로 운영한다고 가정하면, 트래픽이 급증할 경우 자동으로 4개로 증설하고, 트래픽이 다시 감소할 경우 2개로 다시 축소하는 것이다.
        - 오토 스케일링의 목적은 느려지지 않게 성능을 유지하고, 필요한 만큼 사용하여 비용을 절감하고, 사람이 직접 개입하지 않고 자동으로 대응하게 만드는 것이다.
    - ECS Service Auto Scaling
      
        - Application Auto Scaling 서비스를 활용하여 ECS 서비스의 Task 개수를 자동으로 늘리거나 줄이는 기능.
        - CloudWatch가 메트릭을 감시하고, 임계값 초과 시 자동으로 Task를 추가하고, 여유로우면 자동으로 Task를 제거.
        - 세 가지 Auto Scaling 방식을 지원하며 다음과 같다
          
            - Target Tracking(목표값 추적)
            - Step Scaling(단계별 조정)
            - Scheduled Scaling(예약 스케일링)입니다.
    - Target Tracking Scaling Policy
      
        - Target Tracking은 목표 메트릭 값을 설정하면 AWS가 자동으로 CloudWatch 알람과 스케일링 조정을 관리하여 해당 값을 유지하는 방식이다.
        - 보일러가 온도를 유지하는 것처럼, **CPU 사용률 70% 유지**라고 설정하면, CPU가 80% → 자동으로 Task를 추가, 60% → 자동으로 Task를 제거.
        - 다른 방식과 달리 복잡한 CloudWatch 알람을 직접 만들 필요 없이 목표값 하나만 설정하면 되므로, 가장 간단하고 AWS가 권장하는 방식이다.
        - 애플리케이션 가용성을 보장하기 위해 메트릭에 비례하여 빠르게 **스케일 아웃**이 이루어 지지만, **스케일 인**은 더 보수적으로 점진적으로 수행한다.
        - 대기 시간을 설정하여 급격한 용량 변화를 방지하는데, **스케일 아웃**은 빠른 대응을 위해 60초, **스케일 인**은 안정성을 위해 300초로 설정하는 것이 일반적이다.

### ✧  네트워크 격리와 심층 방어

- 🔭 탐구 질문
    
    **1. Public vs Private Subnet** (직접 조사 필수)
    
    많은 학생들이 이 개념을 헷갈려합니다. 정확히 이해하는 것이 중요합니다.
    
    - Public Subnet의 정의는 무엇인가요? "Public IP가 있다"가 정의일까요?
        
        → 인터넷 게이트웨이로 라우팅되는 서브넷 
        
    - Private Subnet의 정의는 무엇인가요? Route Table과 어떤 관계가 있나요?
        
        → 인터넷 게이트웨이로 직접 라우팅하지 않는 서브넷 ( Route Table에 인터넷 게이트웨이를 포함하지 않음)
        
    - Private Subnet에 있는 ECS Task가 어떻게 Docker Hub에서 이미지를 받을 수 있나요?
        
        → ECS Task(Private Subnet) → NAT (Public Subnet) → IGW → Docker Hub
        
    - NAT Gateway는 어떤 역할을 하며, 왜 Public Subnet에 있어야 하나요?
        
        → NAT Gateway는 Private Subnet에서 외부 요청이 필요할 때 외부와 통신을 할 수 있도록 합니다.
        
        → NAT Gateway는 외부와 통신하기 위해 인터넷 게이트웨이가 있는 Public Subnet에 있어야합니다.
        
    - Route Table은 정확히 무엇이고, Public과 Private에서 어떻게 다르게 설정되나요?
        
        → Route Table은 서브넷이 목적지로 트래픽을 보낼 때 어떤 경로로 보내야 하는지를 정의한 라우팅 규칙 집합
        
        → Public Subnet은 인터넷 게이트웨이를 포함하여 설정됩니다. (인터넷 게이트웨이를 포함해야만 Public Subnet)
        
        → Private Subnet은 NAT Gateway를 포함할 수 있고 인터넷게이트웨이는 포함할 수 없습니다.
        
    
    **2. 개발자는 Private DB를 어떻게 관리하나요?**
    
    데이터베이스가 Private Subnet에 있으면 개발자가 직접 접속할 수 없습니다. 어떻게 관리할까요?
    
    - Bastion Host (Jump Server)란 무엇이고, 왜 필요한가요?
        
        → Public Subnet에 위치하며 Private Subnet 리소스에 접근하기 위한 역할을 하는 서버.
        
        → Private Subnet에 개발자가 직접 접근할 수 없으니 Bastion Host(Public Subnet)을 통해 접속
        
    - Bastion Host를 통한 접속 과정은 어떻게 되나요? (단계별로 설명)
        
        → 1. Pulbic Subnet에 ssh 접속
        
        → 2. Private Subnet RDS에 접속
        
    - Bastion Host 자체는 어떻게 보호하나요? 누구나 SSH로 접속할 수 있으면 안 되잖아요?
        
        → 특정 IP에서만 SSH로 접속 가능하게 Bastion Host Security Group을 설정
        
    - SSH 키 파일은 어떻게 안전하게 관리해야 하나요?
    
    **3. Security Group 설계**
    
    Security Group은 AWS에서 가장 중요한 보안 도구 중 하나입니다. 제대로 설계해야 합니다.
    
    - 왜 ALB, ECS Tasks, RDS, Bastion Host가 각각 별도의 Security Group이 필요한가요?
        
        →서로 다른 목적과 보안 범위를 가지므로 SG를 분리해야 합니다. ex) ALB는 인터넷에서 들어오는 80/443을 허용해야 함
        
    - RDS Security Group의 Inbound 규칙을 설계하세요. 누구에게 3306 포트를 허용할 건가요?
        
        → ECS Tasks Security Group
        
    - Security Group을 Source로 지정하는 것은 무슨 의미인가요? IP 주소 대신 왜 이렇게 하나요?
        
        →IP가 아니라 특정 SG를 가진 인스턴스만 접근 가능 하도록 제한하는 것
        
        → 내부 IP는 바뀔 수 있음. 또한 새로운 Task가 정의되더라고 같은 SG에 있으면 따로 추가하지 않아도 됨
        
    - ECS Tasks Security Group은 어떤 Inbound와 Outbound 규칙이 필요한가요?
        
        → Inbound ALB SG
        
        → Outbound RDS SG, 0.0.0.0/0 (NAT)
        
    
    **4. 공격 시나리오 대응**
    
    실제로 공격이 들어온다고 가정하고, 방어할 수 있는지 검증해보세요.
  
    - 시나리오 1
    ```
    해커가 전 세계의 IP에서 포트 스캔 봇을 돌려서 MySQL 3306 포트를 찾으려 합니다.
    
    - RDS가 Private Subnet에 있으면 어떻게 막히나요?
        
        → Internet Gateway 에 연결되어있지 않아 외부에서 접근이 불가
        
    - IP 주소를 모르면 포트 스캔이 불가능한 이유는?
        
        → 포트는 IP 주소 위에서만 존재
        
        → Public IP가 없기 때문에 포트 스캔 대상이 아님
        
    - 설령 내부 IP(10.0.x.x)를 안다 해도 왜 접근할 수 없나요?
        
        → 외부에서 Private Subnet으로 접근할 수 있는 경로가 없음
        
        → 또한 접근이 가능한 경로가 (없겠지만) 있더라도 RDS SG Inbound 정책에서 막힘
    ```
    - 시나리오 2
    ```
    애플리케이션에 SQL Injection 취약점이 있어서 해커가 코드 실행에 성공했습니다.
    
    - 해커는 이미 ECS Task 안에 들어왔습니다. DB 데이터를 전부 삭제할 수 있나요?
        
        → 애플리케이션이 사용하는 DB 사용자 계정 권한에 따라 다를 수 있음
        
    - Security Group은 네트워크 계층 방어이므로 이미 안에 들어온 해커는 막지 못합니다.
    - 어떻게 추가로 방어할 수 있나요? (힌트: DB 사용자 권한)
        
        → 업무상 필요한 최소한의 권한만 부여된 계정을 사용
        
        → ex) 필요한 테이블에 대한 SELECT/UPDATE/INSERT , DROP/GRANT 등은 권한에 추가하지 않음 
    ```
    - 시나리오 3
    ```    
    주니어 개발자가 실수로 RDS 설정에서 "Public Access: Yes"를 켰습니다.
    
    Public Access를 Yes로 켰을 때
    
    1. RDS에 Public IP가 부여됨
    2. RDS가 Internet Gateway를 통해 인터넷과 통신 가능한 상태가 됨
    3. Security Group에서 외부 IP를 열어주지 않았다면 실제로 접근은 불가
    
    - 시스템에 구멍이 뚫렸나요?
        
        → 위험하지만 즉시 침해된 것은 아님
        
    - Security Group이 여전히 작동하나요?
        
        → 네, RDS Security Group Inbound에 ECS SG 또는 Bastion SG만 있을 경우 인터넷에서는 접근 불가
        
    - 이런 실수를 어떻게 방지할 수 있나요?
        
        → IAM 정책에서 RDS 생성 시 PubliclyAccessible=true를 금지
        → RDS Security Group을 항상 SG 기반 접근으로만 운영
    ```
