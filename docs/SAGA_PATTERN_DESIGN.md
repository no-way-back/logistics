# 1. 시나리오 선택 및 분석

## 1-1. 시나리오 분석 문서

### 📋 선택한 시나리오
    
**시나리오 D : 장바구니 → 주문 전환**
    
```bash
[상황]
- 고객이 장바구니에 상품 3개 담음
- 결제 버튼 클릭
- 이 시점에 재고 확인 & 가격 확인 필요
    
[처리해야 할 것들]
1. 장바구니 상품들 재고 확인
2. 현재 가격 확인 (장바구니 담을 때와 다를 수 있음)
3. 재고 예약 (임시 홀딩)
4. 결제 진행
5. 결제 완료 → 재고 확정 차감
6. 결제 실패/이탈 → 재고 예약 해제
    
[실패 시나리오]
- 3개 중 1개만 품절 → 부분 주문? 전체 취소?
- 결제 중 가격 인상됨 → 어느 가격으로?
- 재고 예약 후 10분간 결제 안 함 → 예약 해제
- 동시에 100명이 재고 1개 상품 주문 → 누가 가져가나?
```

---

### 🔧 관련 서비스
- **장바구니** 서비스
  - 역할 : 사용자가 구매하고자 하는 상품 목록을 관리하고, 결제 시 주문 후보 데이터를 제공
  - 관리 데이터 : 상품 ID, 수량, 가격, 유저 ID
        
- **상품** 서비스
  - 역할 : 상품에 대한 정보 제공
  - 관리 데이터 : 상품 정보(판매 가격 등)
        
- **재고** 서비스
  - 역할 : 재고 확인, 재고 예약 및 확정, 예약 해제
  - 관리 데이터 : 상품 ID, 상품에 대한 재고 수량, 예약 상태, 예약 TTL
        
- **주문** 서비스
  - 역할 : 사용자가 결제 의사를 확정한 장바구니 데이터를 기반으로 주문을 생성하고 관리
  - 관리 데이터 : 주문 ID, 유저 ID, 상품 스냅샷 목록, 주문 금액, 배송지, 주문 상태, 결제 ID
        
- **결제** 서비스
  - 역할 : 주문 서비스에서 생성된 주문에 대해 실제 결제
  - 관리 데이터 : 결제 ID, 주문 ID, 유저 ID, 결제 금액, 결제 수단 정보, 결제 상태, PG 승인 번호
   
---
     
### ➡️ 정방향 트랜잭션
- 주문 → 장바구니 → 상품 → 재고 → 결제
- 주문 생성(`PENDING`) → 장바구니 상태 변경 (`ORDER_PENDING`) → 상품 가격 확인 → 재고 예약(`HOLDING`) → 결제 준비(`PENDING`) → 결제 완료(`COMPLETED`) → 재고 확정(`RESERVED`) → 장바구니 상품 삭제(`DELETED`) → 주문 완료(`COMPLETED`)
   
---
 
### 🚫 실패 지점
- 가격 변동
  - 발생 상황 : 장바구니에 상품을 담았을 떄의 시점과 실제 가격이 불일치
  - 영향 범위 : 주문, 장바구니
          
- 결제 실패
  - 발생 상황 : 외부 결제 API가 잔액 부족 등의 이유로 실패
  - 영향 범위 : 주문, 재고, 장바구니
          
- 결제 이탈
  - 발생 상황 : 재고 예약 후 10분 내에 결제 안 함
  - 영향 범위 : 주문, 재고, 장바구니
          
- 재고 예약 실패
  - 발생 상황: 재고 없음
  - 영향 범위: 주문, 장바구니
    
---
      
### 💰 보상 트랜잭션
- 가격 변동
  - 보상 액션 : 장바구니 상태 롤백 (`ORDER_PENDING` → `ACTIVE`) → 주문 상태 변경(`PENDING` → `FAILED`)
          
- 결제 실패
  - 보상 액션 : 재고 예약 해제(`HOLDING` → `AVAILABLE`) → 장바구니 상태 변경 (`ORDER_PENDING` → `ACTIVE`) → 주문 상태 변경(`PENDING` → `FAILED`)
          
- 결제 이탈
  - 보상 액션 : 재고 예약 해제(`HOLDING` → `AVAILABLE`) → 장바구니 상태 변경 (`ORDER_PENDING` → `ACTIVE`) → 주문 상태 변경(`PENDING` → `FAILED`)
          
- 재고 예약 실패
  - 보상 액션 : 장바구니 상태 롤백 (`ORDER_PENDING` → `ACTIVE`) → 주문 상태 변경(`PENDING` → `FAILED`)

# 2. 설계 점검 체크리스트

## 2-1. 멱등성 (Idempotency)

- 같은 환불/취소 요청이 2번 오면 어떻게 처리하는가?
  - 이미 처리된 요청인 경우, 동일한 응답을 제공
      
- 중복 요청을 어떻게 식별하는가?
  - 같은 요청이 여러 번 오더라도 한 번만 처리되도록 강제하는 키(멱등키)를 사용
  - 서버는 해당 키로 이미 처리된 기록이 있는지 DB나 Redis에서 조회

---

## 2-2. 타임아웃 & 재시도

- 외부 API(카드사, PG) 응답이 오지 않으면 얼마나 대기하는가?
  - 3초 이하
      
- 재시도는 몇 번까지, 어떤 간격으로 수행하는가?
  - 재시도 3번
  - 1 ,3, 5초 간격으로 수행
      
- 재시도를 해도 계속 실패하는 경우, 최종적으로 어떻게 처리하는가?
  - 결제 상태를 FAILED와 같은 값으로 변경하여 관리자 처리

---

## 2-3. 부분 실패

- 5단계 중 3번째에서 실패하면 1번, 2번은 어떻게 처리하는가?
  - 보상 트랜잭션을 수행
      
- 보상 트랜잭션 실행 순서는 어떻게 구성되는가?
  - 트랜잭션의 역순으로 수행
      
- 보상 트랜잭션도 실패할 경우 어떻게 처리하는가?

  ⓵ Outbox 기반 재시도

  ⓶ 재시도 3회 실패시 DLQ 로 이동 후 관리자 확인

---

## 2-4. 상태 관리

- 현재 트랜잭션이 어느 단계인지 어떻게 알 수 있는가?
  - Saga 또는 Outbox 테이블에 현재 진행 중인 트랜잭션 저장
      
- 중간에 서버가 죽었다가 재시작하면 어디서부터 이어가는가?
  - 서버 중단 직전에 발행된 이벤트부터 수행

---

## 2-5. 예외 케이스

- 장바구니 3개 중 1개만 품절이면 어떻게 안내하는가?
  
  - 전체 주문 실패 (예 : `일부 상품이 품절되어 주문이 불가합니다.`)
  
  - 주문 가능한 상품만 구매 진행 (예 : `A 상품이 품절되어 구매가 불가능합니다. 구매 가능한 상품만 구매하시겠습니까?`)

# 3. 아키텍처 설계

## 3-1. 패턴 선택 및 근거
- [X] **Orchestration**
- [ ] Choreography
      
- 선택 근거
  - 주문 → 재고 → 결제 의 순서는 반드시 지켜져야 함
  - 순서를 건너뛸 수 없고, 각 단계가 이전 단계의 성공을 전제하므로 Orchestrator가 중앙에서 흘러가는 순서를 명시적으로 통제해야 함
